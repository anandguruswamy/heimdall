Here is my idea for a generic beacon protocol that supports any number of boards, let's discuss and refine it.

Assume there are a total of N boards. Refer to the boards as B_1,...,B_N.

Protocol hierarchy consists of superslots consisting of one or more slots.

Superslots are counted by sequence counter k (k=0,...,2^16-1).

A superslot consists of M consecutive slots. Slots inside a superslot are indexed by m=0,..,M-1

Any board B_i can only transmit in a superslot where the condition [k modulo N = i] is satisfied.

When B_i transmits in superslot k, it transmits a pooled report P_i
 1. U_(i,1), U_(i,2),..., U_(i,N) (all except U(i,i))
 2. Tx_timestamp
 3. k
 4. CRC for whole message

Here U_(i,j) is a single subreport generated by B_i receiving from B_j in slot index k - mod(i-j,N). 
It contains the following:

U_(i,j) = {j, CIR_(i,j), first_path_index_(i,j), Rx_timestamp_(i,j), CFO_(i,j), DGC_Gain_State_(i,j)} for j in {1,2,3,4,5,..,N} , j != i.

Notes:
1. At a high level (before we build the firmware), we defined the payload length, slot duration, number of CIR taps, CIR left/right window. The superslot size M is automatically computed based on the number of slots required to send a pooled report of max size. 

2. Pooled reports may not always be full size -- for example if B_i misses one or more slots of the last superslot where B_j was transmitted, then the pooled report P_i will omit U_(i,j).

3. Timestamp counter rollovers are handled automatically.

4. Board B_1 will be connected to the Uno Q and can be treated as the master board. B_1 always transmits in its superslot. Board B_i for i != 1 only transmits in its superslot if either
  a) It receives a message from B_1 in its last scheduled superslot.
  b) It receives a message from a node B_j in its last scheduled superslot, and B_j's pooled report contained a subreport corresponding to B_1. 
  Here the idea is that if none of the boards can see board 1, they all stop transmitting. If any board can see at least one other board receiving from board 1, it will continue.

5. Initial Sync:
   1) B_1 when turned on starts transmitting all the time in its scheduled slot. Its superslot counter k is the golden reference.
   2) When another B_i for i!=1 is turned on, it waits to receive a message from any board. When it receives a message, it derives current superslot index from the message and is then synchronized. (Lets start with all UWB receivers using always listening mode. Later we can consider switching from always listening mode pre-sync to slot-gated Rx mode post-sync). 


The idea is to have a html page where parameters like N, payload length, slot duration, number of CIR taps, CIR left/right window can be entered, and resulting superslot structure is visualized, and per link report rate in Hz is also shown. User plays around with values, and when a good strucutre is found, he can click an export button to export the config in a nice human readable format. The build system derives parameters from a specified config file.
